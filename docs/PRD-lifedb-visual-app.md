## 1. Summary

本文档定义「大记理论」在 kernel 数据层已打通后的下一步：**可视化层**（一个可交互的本地地图/时间轴界面）与**应用层**（跨数据源组合出的具体应用：旅行 vlog 一键导出、TrainCoach 健身视图）。核心命题是：数据已经归一到一张 `event` 表 + 一张 `geo_point` 表，现在要让它**看得见、能玩、能分享**，并以此验证"打通不同数据源"这件事到底能产生什么别人做不到的东西。

## 3. Background

**已经做到的（Phase 1，全部实测）**：
- 单 SQLite 库 `timeline.db`：GPS 停留段 833 + 秒级点 294,811 + 训练日 125 + Google Timeline 106 + 照片 30（云端全库 13,994，同步策略待定）
- 四个模态（GPS / 健身 / 交通 / 照片）已归一 schema：`ts_start | ts_end | modality | source | lat | lon | meta`
- iCloud 认证与时间窗下载已自动化

**为什么是现在**：
1. **数据主权是卖点**：Google 2024 年把 Timeline 改为设备本地存储并砍掉桌面版网页，几亿用户的"年度足迹地图"没了。用户被迫接受"数据在别人服务器上，随时可能消失"。local-first + OSM（零 API key）恰好接住这个空缺。
2. **个人数据 Wrapped 成为文化现象**：Spotify Wrapped / Strava 年度总结 / Apple Fitness 年报证明"把自己的数据变成可分享的故事"有自发传播力。但这些都锁在大厂 App 里，且只有单一模态。
3. **参考生态已成熟**：GoogleMapTimelineViewer2 证明纯前端 + OSM + Timeline.json 就能做出流畅的多年轨迹回放；kepler.gl/deck.gl 证明百万点级渲染在浏览器可行；Immich（108K stars）证明自托管照片库有巨大需求。**但没有一家把"轨迹 + 照片 + 训练 + 笔记"放在同一时间轴上**——这正是 LifeDB 的独占数据结构。

**用户明确的 taste（不可违背）**：
- 可视化层 = **可交互的本地单文件 HTML**，或 **localhost 起服务**登录交互查看。目标是"能录屏发社媒引发讨论"，不是内部工具。
- 应用层两个方向：**旅行照片×坐标一键导出 vlog**；**TrainCoach（健身房位置×照片×训记合并）**。
- 重点是**打通不同数据源**，不是单模态做得漂亮。

## 4. Objective

**O：让 LifeDB 从"能查的库"变成"能看、能玩、能分享的个人宇宙"，并用可传播的产出物验证跨模态数据的价值。**

Key Results（SMART）：
- **KR1**：产出一个可运行的可视化 v0.1——打开一个 URL（localhost）或双击一个 HTML，10 秒内看到自己多年的轨迹+照片在同一张地图上，时间滑块可拖动。验收：用户本人愿意录屏发一条社媒。
- **KR2**：一键导出功能 v0.1——选一个日期窗（如"首尔 2026-10"），自动产出一段 ≥30 秒的旅行 vlog（地图动画 + 照片序列 + 轨迹线），全程无人工剪辑。验收：产出物可直接发布。
- **KR3**：TrainCoach v0.1——把"健身房停留段 + 当天训记动作/重量 + 当天健身房照片"合并成一个训练日视图。验收：用户看一个训练日能回忆起当天全部上下文。
- **KR4（传播）**：至少一个"年度 Wrapped"式分享卡（如"2026 我的足迹：X 个城市 / Y 公里 / 最常去的咖啡馆"），9:16 竖版图，一键生成。

## 5. Market Segment(s)

按"要完成的活"分，不按人口统计：

| Segment | 他们的活（Job） | 现有方案的痛 | 我们怎么赢 |
|---|---|---|---|
| A. 自我量化 / Lifelog 玩家 | 把散落的个人数据统一归档、可视化、可查询 | Google Timeline 没了网页版；各家数据锁在各自 App；自己写代码门槛高 | 一键归一 + 本地可交互地图，数据永不上传 |
| B. 想在社媒发"足迹/年度总结"的人 | 产出有美感、可炫耀的个人数据内容 | 只有大厂 App 的固定模板 Wrapped，无法自定义、无法私有 | 自定义 Wrapped 卡 + 可录屏的交互地图（差异化极强） |
| C. 旅行者 | 回顾旅行、快速产出旅行 vlog | 手动剪辑几小时；MapAnim/Google Earth Studio 要上传服务器或付费 | 本地一键从"照片+轨迹"生成，隐私零上传 |
| D. 力量训练者 | 看到"练得怎么样+体型变化"的关联 | GainFrame 等 App 只连了 Hevy 一个数据源；训记/位置/照片是割裂的 | 跨源合并（健身房位置×训记×照片），且完全本地 |

**约束**：
- 数据主体只有 1 人（用户自己）——但目标是**产出物可传播**（录屏/分享卡），用个人故事撬动讨论，不是做 SaaS。
- 存储：D 盘仅剩 43G，全库 13,994 张装不下 → 分层策略未定，影响"全量照片上图"的能力，v0.1 先用已下载子集。

## 6. Value Proposition(s)

**核心 jobs**：
1. **"看见我自己"**——把 11 年、29 万个位置点、上千次训练、上万张照片，变成一眼能看懂的图景。
2. **"讲我的故事"**——一键产出能发社媒的内容（足迹图、年度卡、旅行 vlog）。
3. **"记住那一天"**——点开任一训练日/旅行日，位置、照片、笔记、训练全部浮现（跨模态关联）。

**解决得比对手好的点（Value Curve）**：

| 能力 | LifeDB | Google Timeline | Immich | MapAnim/GainFrame |
|---|---|---|---|---|
| 跨模态同轴（位置×照片×训练×笔记） | ✅ **独占** | ❌ 只有位置 | ❌ 只有照片 | ❌ 单模态 |
| 本地/数据主权 | ✅ 全本地 | ❌ 云端（已砍桌面版） | ✅ 自托管 | ❌ 上传服务器 |
| 零 API key / 零成本部署 | ✅ OSM | ❌ | ⚠️ 需服务器 | ❌ 付费 |
| 可自定义的分享产出物 | ✅ | ❌ 固定模板 | ❌ | ⚠️ 有但单一 |
| 一键 vlog（照片+轨迹→视频） | ✅（Phase 2） | ❌ | ❌ | ✅ 但要上传 |

**用户获得**：隐私零妥协的自我可视化 + 社媒可炫耀的产出物 + "这是我自己的数据做的"叙事资本。
**避免的痛**：数据被平台锁死/消失、上传第三方服务器、手动剪辑数小时、订阅付费。

## 7. Solution

### 7.1 UX / 用户流

**入口双形态（同一套代码）**：
- **形态 A · 单文件 HTML**：`python life-db export --html atlas.html` → 生成一个自包含 HTML（数据内嵌或同目录 JSON），双击即开，可发给别人/存 U 盘/录屏。隐私最极致。
- **形态 B · localhost 服务**：`python life-db serve` → 起本地服务（如 127.0.0.1:8787），浏览器打开交互式查看，数据实时读 `timeline.db`（只读），支持大数据量分页加载。

**主视图（Life Atlas）**：
```
┌────────────────────────────────────────────┐
│  [地图 deck.gl/MapLibre + OSM]              │
│   轨迹线 / 停留点热力 / 照片缩略图上图       │
│                                            │
│   点击任一元素 → 侧栏浮出该时刻的跨模态卡片  │
│   （同一天的训练/照片/停留/笔记）            │
├────────────────────────────────────────────┤
│  ⏮ ▶ [======●──────────] 时间滑块 2015→今  │
│  [年份] [月份] [模态开关: 位置/训练/照片/…] │
└────────────────────────────────────────────┘
```
- **时间滑块**：拖动即回放（deck.gl TripsLayer/路径动画），参考 GoogleMapTimelineViewer2 的 Time Slider Animation。
- **跨模态卡片**：这是差异化核心——点一个红点，右侧同时出现"那天你练了深蹲 5×5 / 在这家咖啡馆拍了 3 张照 / 停留 1.2 小时"。
- **一键导出按钮**：当前视图/日期窗 → [分享卡] [KML/KMZ] [旅行 vlog]。

**应用层视图**：
- **旅行 vlog 编辑器（极简）**：选日期窗 → 自动聚类出"这趟旅程"（按停留段切分）→ 预览地图动画+照片序列 → 一键导出 MP4。参考 MapAnim（GPX→动画）但用我们自己的 `event` 表。
- **TrainCoach**：选一个训练日 → 三栏（健身房位置卡 / 训记动作表 / 当天健身房及周边照片）。跨源 join：`event(modality=workout)` 的日期 ⟷ `event(source=photo)` 同日 ⟷ 停留段中"疑似健身房"的 geo_point。

### 7.2 Key Features

**P0（v0.1，验证核心价值）**
- F1 全局地图 + 时间滑块回放（轨迹/停留点/照片缩略图三图层，可开关）
- F2 跨模态时刻卡片（点击任一元素聚合该时刻所有模态）
- F3 单文件 HTML 导出 + localhost 服务双形态
- F4 9:16 分享卡一键生成（"我的足迹"年度/月度摘要，含地图缩略+关键数字）

**P1（v0.2，应用层差异化）**
- F5 旅行 vlog 一键导出（地图动画 + 照片序列 + 轨迹线 → ffmpeg 合成）
- F6 TrainCoach 训练日视图（位置×训记×照片三源合并）
- F7 KML/KMZ 导出（时间过滤，参考 GoogleMapTimelineViewer2，可嵌缩略图）

**P2（远期）**
- F8 笔记/Obsidian 模态接入后的时间轴全文检索
- F9 "本周回顾"自动推送（cron 每周生成一张卡发飞书）
- F10 多端（手机 localhost 局域网访问 / PWA）

### 7.3 Technology

- **渲染**：deck.gl + MapLibre GL + **OSM 底图（零 API key，serverless）**——直接借鉴 GoogleMapTimelineViewer2 的架构选择（Vite + TS + 纯前端）。29 万点用 deck.gl 的聚合/图层能力（deck.gl 官方：可渲染百万点）。
- **数据供给**：localhost 用 Python 轻服务（FastAPI/Flask）读 `timeline.db` 只读，按视口/时间窗做 SQL 分页（遵守 kernel 效率约定：range seek，禁 LIKE 前缀）。单文件 HTML 则把筛选后的数据内嵌为 JSON。
- **vlog 合成**：地图动画用 deck.gl 离屏渲染/Manim，照片序列+转场用 ffmpeg（本机已有）。参考 MapAnim 的"GPX→动画"思路，但数据源是我们的 `event` 表。
- **分享卡**：HTML/CSS → Chrome headless 截图 → JPEG（复用已有 `xhs-image-pipeline` 技能）。
- **照片上图**：复用 photo adapter 已提取的 EXIF GPS（`event.lat/lon`）；参考 GoogleMapTimelineViewer2 的 Photo Viewer（cluster + 缩略图尺寸可调）。
- **部署**：零云端、零订阅。OSM 瓦片公开源 + 本地数据。

### 7.4 Assumptions（待验证）

1. **A1**：用户愿意把 localhost 界面录屏发社媒（→ KR1 验收即验证；若不愿，说明界面不够美/不够有叙事，需迭代视觉）。
2. **A2**：跨模态关联（照片×位置×训练）在 UX 上真的有用，而不只是"能 join"。（→ KR3 验收验证）
3. **A3**：旅行 vlog 自动产物的质量能达到"可直接发布"，无需人工修饰。（→ KR2 验收验证；若达不到，需加一个极简人工挑选步骤）
4. **A4**：OSM 公开瓦片源对个人量级足够，不会被限流。（低风险，可换自托管瓦片）
5. **A5**：13,994 张照片的分层存储策略能在 v0.1 期间保持"照片上图"可用（先用已下载子集即可，不阻塞）。

## 8. Release

避免绝对日期，用相对时间框：

- **v0.1（约 1–2 周）**：P0 = F1–F4。目标：一个能跑的 Life Atlas + 分享卡。验收 = KR1 + KR4。**这是最小可传播单元，优先做。**
- **v0.2（约 2–4 周）**：P1 = F5–F7。目标：旅行 vlog + TrainCoach。验收 = KR2 + KR3。
- **v0.3+（远期）**：P2。等 Obsidian/OneDrive 模态接入后再扩。

**v0.1 明确不做**：多用户/账号体系、移动端 App、云端部署、AI 自动叙事（先手动规则）。这些都会稀释"本地、私有、跨模态"的核心差异。

**最大风险**：v0.1 的视觉质量不足以引发社媒传播（A1 失败）。缓解：v0.1 就把"分享卡"作为一个独立的一等公民来做（美学是硬要求，不是附赠），并尽早用真数据录屏验证。

### 附A：红队审查结论（2026-10-13，strategy-red-team）

**结论：方向不变，照此开发。** 5 条承重假设全部经受住攻击（市场空缺有据、schema 支撑 join、TrainCoach 训记有毫秒级 start/end 可做时间重叠 join、范围克制、视觉风险已自我标注）。以下为执行层修订，开发时遵守：

1. **照片上图定位策略改写（F1）**：实测 EXIF GPS 覆盖率仅 8%（34 张中 3 张，微信图/截图不带 GPS）→ 照片层主方案改为**时间戳回溯定位**（照片 `ts_start` ⟷ `geo_point` 最近点插值），EXIF GPS 作为优先输入。此 join 本身即跨模态卖点，实现时写进技术方案。
2. **F4 分享卡优先级前置**：先用真数据做 3 张静态分享卡验证"自己想不想发"，结果决定 v0.1 内部排序——美学方向的验证要比地图代码更早。
3. **F5 vlog 验收措辞松动**：KR2 从"可直接发布"放宽为"一键出草稿，人工精修 < 10 分钟"（行业先例：Google Photos/GoPro Quik 自动剪辑发布率低）——试跑后若质量超预期再收紧。
4. **瓦片降级预案**：OSM 公开瓦片国内速度未验证；若 P95 > 2s → 依次降级：内嵌瓦片切片进 HTML → 国内 CDN 镜像 → 静态深色底图。分享 HTML 不依赖 GitHub Pages（国内打不开）。
